# 个人模式的持续改进

来源包括automate-me、reflect、correct。先区分“提炼偏好”和“证明方法有效”。偏好来自人的明确话语，Agent代写、重复profile、父Agent派单不算独立用户证据。

建立或重做模式：检查现有模式，按时间段/项目分片读已授权历史；默认当前工作区，本次全盘扫描授权不能成为以后默认。候选跨至少两个独立切片出现才提为高置信习惯；反例、过期偏好和当前修正一起保留。缺失偏好少量提问，不问已有证据能回答的事实。

任务后复盘：只分析当前会话实际使用的技能和工具。复杂任务用三个独立视角：判断偏差、工具/流程、反常替代解释。负责人核实每条证据，输出Accepted/Rejected/Backlog及原因。

有当前技能修改授权才落地Accepted；已有明确授权不重复索要。无授权只给可审建议。确定性约束优先进入类型、元数据、lint或脚本，不叠加永远禁令。单次纠错先范围内修正，项目规则仅在合适授权和重复证据后更新。记忆和理论母本有自己的修改边界。

更新后跑行为验证、记版本与回退方式；真实反馈与事前目标比对，避免因喜欢某规则就宣称有效。

## 反复错误的结构化修复

错误至少重复两次时按类归并，回查真实提交、回退、评论与用户纠正。优先级是：架构消除多个状态源/错误入口→类型使坏状态不可构造→lint或CI指出具体正确入口→行为测试→只能靠判断的文档规则。

每个新增检查必须在一个真实历史错误上失败，再证明当前修复通过；用相同命令本地与CI运行。旧错误很多时先限制新增，而非突然阻断全部遗留。记录规则与实际执行器映射；已由结构消除的冗余指令可删。例外写原因和期限，不能永久逃逸。处理范围内最频繁错误，不以纠偏为由无边界重构。
