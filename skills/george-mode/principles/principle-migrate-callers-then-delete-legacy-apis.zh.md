# 先迁移调用方，再删除旧 API（Migrate Callers Then Delete Legacy APIs）

当我们确定新 API 是正确的设计时，在同一波重构中迁移调用方并移除旧 API，而不是保留兼容层。

**规则：**
- 不要仅仅因为仍有内部调用方就保留旧 API 路径
- 盘点调用方，迁移它们，并立即删除旧 API
- 把临时适配器视为例外并设定时限，而不是默认架构
- 更新测试以断言新契约，删除只保护重构前实现细节的测试

**适用条件：**
- 没有外部用户依赖向后兼容
- 项目能够承受协调一致的破坏性变更
- 新 API 是某项简化或重构计划的一部分

同时保留新旧 API 会造成双路径复杂度，拖慢清理，并让代码库变得只增不减。

## George 适用边界

保留原文的适用前提：没有外部消费者、允许协调破坏性变更。线上协议/数据迁移分阶段，旧 API 删除条件事前明确。
