# 修根因（Fix Root Causes）

调试时，修复故障本身，而不是它显露出来的地方。症状是错误状态变得可见的地方；根因是系统第一次做了不该做的事，或没有处理本应处理的状态的地方。

**为什么：** 修症状会掩盖证据，并让故障在别处自由冒出来。每一次这样的修补都让系统更难推理，因为代码里多了一个针对无人命名的 bug 的变通。

**做法：**
- 先复现。
- 每一步都问“为什么”，直到答案是代码中的一个错误决定，而不是更早错误的后果。
- 卡住时加观测。读取真实的错误和真实的状态，不要猜。
- 问触发症状的那个状态是否合法。如果系统可能处于该状态，那么在该状态上崩溃的代码就是根因，在那里处理该状态就是修复。如果该状态本不该存在，在崩溃处加检查就是掩盖 bug；去找产生该状态的地方。守卫、重试、吞掉的错误、被截断的值和被丢弃的状态，是掩盖 bug 的常见方式。
- 当某事只在重启后失败时，首先怀疑持久化状态：配置文件、缓存、锁文件、序列化状态。
- 检查模式，而不仅是实例。找出所有存在同一故障的地方，全部修复。
- 如果一个变通需要一整段注释来辩护，那么错的是代码。修代码，不是修注释。
- 如果决定性的事实需要深挖才能找到，就提出一个廉价、常开的信号，让它第一眼就能显示出来。

## George 适用边界

按触发场景应用；结果有证据、适用边界和反例。重要现实决策接理论闭环，普通工程不强制全套经营记账。
