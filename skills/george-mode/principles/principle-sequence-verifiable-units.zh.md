# 把工作排成可验证的单元（Sequence work into verifiable units）

把工作排成一串小单元，每个单元都以一个可检查的状态结束；当前单元未通过（变绿）之前不要前进。

**为什么：** 在引发问题的单元处发现故障，定位成本很低。在一整批之后才发现的故障被埋住了，而你已经在坏掉的基础上继续搭建。把同样的单元排成审查者可以重放的交付，就把“相信我”变成了“看它先变红、再变绿”。

**执行。** 在批量清理、迁移或任何一连串相似修改中，开始下一处修改前先验证当前这一处。每个单元都是一对前后括号：已知良好的状态、一次修改、运行检查、然后继续。先建立正确的当前基线；只在需要且对自己拥有的分支安全时才 rebase，不丢弃用户的修改。当由杠杆完成修改时，逐单元检查几乎免费——照样运行。

**交付。** 按能证明工作的顺序堆叠提交和 PR。典型形态是先提交失败的测试，再在其上提交修复。其他叙事顺序包括：重塑之前先做减法、处理之前先采集基线、功能之前先搭脚手架。每个提交都能独立落地，整个序列读起来就是一段论证。

它是 **prove-it-works** 原则技能（保证每次检查真实）和 **build-the-lever** 原则技能（让逐单元检查变便宜）在排序上的补充。

## George 适用边界

按触发场景应用；结果有证据、适用边界和反例。重要现实决策接理论闭环，普通工程不强制全套经营记账。
