# 测行为，不测实现（Test Behavior, Not Implementation）

测试是关于代码为其用户做了什么的断言：调用方、最终用户或另一个服务。行为是这些用户通过他们所使用的接口能观察到的东西，包括返回值、错误、他们能读回的状态，以及对代码之外系统的影响，例如发出的请求、写入的行或发出的消息。实现是他们观察不到的东西：私有辅助函数、内部调用顺序、中间数据，以及由哪个内部协作者完成了工作。

用两种设想的修改来评判每个测试：

- **破坏行为。** 让代码返回错误的值、跳过某个效果或把效果做两次。如果测试仍然通过，它什么也证明不了。常见原因：断言比契约更宽松；期望值由被测代码计算得出；重述了一个常量或提示词字符串，却从不运行读取它的代码；断言的是测试自己构造的数据。
- **改变内部。** 保持每个可观察结果不变，重构底层代码。如果测试因此失败，它就被钉死在实现上：每次重构都要重写，却仍然抓不到任何 bug。

保留能抓住第一种修改、又能挺过第二种修改的测试，其余的重写或删除。要写出两者兼顾的测试，就用具体输入通过用户接口驱动代码；从需求而不是从代码的一次运行推导期望值；断言契约承诺的内容，不多也不少。

决定因素是契约，而不是断言的形状。当承诺是“空购物车绝不扣款”时，断言支付客户端没有被调用就是行为——再配一个确实发生扣款的用例，以表明测试能看到调用。被 mock 的外部服务收到的载荷是行为，因为那个服务能观察到它。对内部辅助函数的调用是实现，因为没有用户能看到。当没有记录匹配时，空列表是确切的答案；而当测试只需要“有某个结果”时，它是一个空洞的检查。精确的错误消息钉住了没有调用方会读的措辞；调用方据以分支的错误类型才是契约。

测试也可以钉住一个不变量而不是一次调用，例如某个键必须同时存在于两张表中，或一次编译期类型检查。不变量就是行为。

## George 适用边界

按触发场景应用；结果有证据、适用边界和反例。重要现实决策接理论闭环，普通工程不强制全套经营记账。
