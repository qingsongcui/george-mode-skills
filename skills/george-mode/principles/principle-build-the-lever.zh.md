# 打造杠杆（Build the Lever）

当工作并非微不足道时，构建一个替你完成它的工具，而不是手工去做。

代码改写工具（codemod）、生成器或脚本每次都以同样的方式完成工作，并且可以免费重跑。工具是审查者能够阅读并重跑以检查工作的单一产物。手工完成的修改只能通过重做来再次验证。确定性的脚本把“相信我”变成“运行这个”。

默认构建杠杆。只有当任务微不足道——几处一眼就能看清的明显修改——时才跳过。

- 先手工完成第一个单元以掌握做法，再构建工具。通过在该单元上重跑工具并与手工版本做 diff 来证明它。让杠杆可以安全地重跑。
- 编辑用 codemod 或脚本，重复文件用生成器，分析用导出到 sqlite 的查询，验证用可重跑的检查。
- 确定性的杠杆胜过分派。如果工具能一次处理所有单元，就自己运行它。不要分派多个代理去手工套用一个脚本就能完成的事。
- 当你把工作分派给子代理时，把杠杆写成一个它们都会读取的技能：做法、验证契约和禁改边界放在同一个产物里。让它位于代理的写入范围之外，免得它们悄悄修改契约。
- 应用本原则会产出一个文件。如果你引用了它，而 diff 中没有 codemod、脚本、生成器或委派技能，你就没有应用它。
- 当工作的生命周期超出本次会话时，提交这个杠杆。

门槛是“是否微不足道”，而不是“是否重复”。一次性的工作，如果杠杆正是让它可检查的东西，也值得构建杠杆。按照 [懒惰协议](principle-laziness-protocol.md)，构建能完成或证明工作的最小脚本，绝不构建框架。

本原则不同于 [把教训写进结构](principle-encode-lessons-in-structure.md)：后者把反复出现的指令变成持久的护栏；本原则关注眼前工作的吞吐量与可审查性。关于把验证本身脚本化，见 [证明它能用](principle-prove-it-works.md)。

## George 适用边界

复用已有工具优先；脚本价值由可重跑证明或减少重复错误决定，不为每个小修改造框架。
