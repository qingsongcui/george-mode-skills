# 类型系统纪律（Type System Discipline）

让编译器拒绝不可能的状态、不匹配的原始类型和未处理的变体。优先通过定义让错误和特例不复存在，而不是不断增加处理器。TypeScript 语法见 `typescript-best-practices` 技能。

- **让非法状态无法表示。** 把变体建模为和类型（可辨识联合、带载荷的枚举、密封类），而不是一袋可选字段——那样矛盾的组合也能编译通过。`{ completed: boolean; completedAt?: Date }` 允许 `completed: true` 却没有日期。应从 `completedAt` 推导布尔值，或建模为 `{ kind: 'open' } | { kind: 'done'; at: Date }`。如果你能写一条注释解释某种字段组合何时有效，就把它拆成和类型。
- **类型是构造，不是限制。** 从你想要的值出发构建类型，而不是用检查从一个更宽松的类型里切出它们。非空列表是一个头加一个余部；有效的时间范围是起点加时长。选择无法构造出非法值的形状，再在其上暴露调用方需要的接口。
- **为语义原始类型打品牌。** `UserId` 和 `OrderId` 底层都是字符串，但不应可以互换。给每个一个独立类型，例如 TypeScript 中的品牌交叉类型或其他语言中的 newtype。在创建时校验一次，下游信任类型。如果两个参数共享原始类型却含义不同，就给它们打品牌。
- **外部数据在解析前是无类型的。** RPC 载荷、JSON、IPC 消息、命令行参数、配置文件、环境变量、数据库行。在每个边界处都要有把非结构化输入转换为有类型模型的解析函数。在哪里放校验，见 **boundary-discipline** 原则技能。
- **不要对类型系统撒谎。** 绕过编译器的强制转换、不安全的类型强转和断言函数，都是潜伏的运行时崩溃。如果编译器无法证明某个事实，就去证明它（校验、收窄、细化模型），或者承认这次转换是个隐患。把每个 `any`、`as` 或 `assertNotNull` 追溯到边界并在那里校验。
- **穷尽匹配是编译器的工作。** 对和类型的匹配，在新增变体而未处理时必须编译失败，这样编译器会告诉下一个代理应在哪里加分支。使用你所用语言的惯用法：TypeScript 中 `never` 类型的绑定、Rust 中不加注解的 `match`、Haskell 中的 `-Wincomplete-patterns`、Kotlin 中密封类匹配的穷尽性。
- **从权威 schema 推导类型。** 当 protocol buffer、OpenAPI 规范、GraphQL schema、数据库迁移、设计 token 文件或其他文件拥有某个形状时，从它推导，而不是手写一个平行类型。见 **encode-lessons-in-structure** 原则技能。
- **只在出现偏函数之处加强类型。** 运行时断言、空值检查或“这不应该发生”的抛出，标记了类型过弱的位置。把那个检查上推到类型里——然后停下。类型系统的工作是追踪每个使用点必须处理的情况，而不是尽可能精确地描述数据。优先全函数：空列表的 `sum` 是 0，所以它接收普通列表；空列表的 `head` 没有答案，所以它要求非空列表。如果没有任何地方会因此 panic，就保持普通类型。
