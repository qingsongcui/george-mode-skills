# 先分离，再串行化共享状态（Separate Before Serializing Shared State）

当并发的执行者可能共享可变状态时，先问它们是否需要同一个可变对象。如果不需要，就消除共享。当共享确实存在时，用结构强制串行化：锁文件、顺序阶段、独占所有权。指令和约定不是并发控制。

**为什么：** 对共享状态的并发写入会产生竞态条件，它们间歇出现、难以复现、调试代价高。

**做法：**
1. **识别共享可变状态**（双方都读写的文件、双方都推送的分支、双方都定义并消费的 API）。
2. **默认：消除共享写入目标。** 问：这些执行者需要一个规范对象，还是在发布相互独立的事实？给每个执行者自己拥有的文件、键、分支或状态目录，只在读取/报告边界处合并。两个 worker 把各自的 `lastX` 字段写进同一个 `state.json`，仍然是共享修改；`indexer-state.json` + `metrics-state.json` 则不是。
3. **只有当单一共享写入目标是真正的不变量时，才用结构串行化访问**（锁文件、顺序阶段、单写入者执行者或原子比较并交换）。把“我们需要一把锁”当作需要检查的设计异味，而不是默认答案。

## George 适用边界

按触发场景应用；结果有证据、适用边界和反例。重要现实决策接理论闭环，普通工程不强制全套经营记账。
