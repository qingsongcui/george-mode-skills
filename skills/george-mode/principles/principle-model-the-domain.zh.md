# 为领域建模（Model the Domain）

把真实领域编码进数据结构，而不是分散在各处条件判断里。与领域匹配的结构让非法状态无法表示，并删除分支。在编写时选择它很便宜；事后再找回它看起来像一次重构，往往会被推迟。

可以选用：

- 用状态机代替分散的布尔值、阶段或生命周期检查。
- 用有类型的模型代替松散参数或重复的形状假设。
- 用映射、注册表、查找表或可辨识联合，代替散布在多个文件里的分支。
- 用 reducer 或命令/事件模型代替临时的状态修改。
- 围绕一块领域知识组织模块，而不是按“加载、校验、转换、保存”之类的顺序组织。执行顺序不等于归属。
- 用一个小的模块边界聚合重复的行为、归属或不变量。
- 在访问模式需要时使用队列、缓存、索引、图、树或规范化集合。
- 任何其他合适的结构。都不合适时，先弄清代码绝不能允许什么、数据如何被读取，再找到恰好编码这些的结构。

不要强行抽象。如果当前形状已经清晰、局部且不太可能增长，就选择朴素的代码。对增加了间接层却没有去掉分支、重复规则、非法状态或生命周期风险的抽象保持怀疑。

跳过这一步的迹象是：新功能让现有 if/else 链再多一个分支，或者出现第二个必须与第一个保持同步的布尔值。按时间分解是另一个迹象：以阶段命名的模块会在各步骤间重复同样的领域规则。

## George 适用边界

按触发场景应用；结果有证据、适用边界和反例。重要现实决策接理论闭环，普通工程不强制全套经营记账。
